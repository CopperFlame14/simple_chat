Theory & Background

What is a Communication Protocol?

A communication protocol is a system of rules that allows two or more entities to transmit information. It defines:

  • Syntax: Structure and format of data (message format)
  • Semantics: Meaning of each section of bits (what each field represents)
  • Timing: When to send data and how fast (synchronization)

OSI Model Context

SCP operates at the Application Layer (Layer 7) of the OSI model, similar to HTTP, FTP, or SMTP. It uses TCP (Transport Layer) for underlying reliable communication.

Key Concepts in SCP

1. Message Format: Structured packets with version, type, ID, and payload
2. Acknowledgments (ACK): Both parties confirm receipt of each message
3. Timeouts & Retries: Sender resends if ACK not received within timeout period
4. Connection Management: Proper setup (HELLO) and teardown (BYE) phases
5. Duplex Communication: Both client and server can independently send and receive messages
💡 Learning Outcome: By implementing SCP, you understand how application protocols work at a fundamental level, including reliability mechanisms and bidirectional communication that protocols like TCP provide at lower layers.

🔧 Protocol Design Specification

SCP Message Format

Every SCP message follows this standardized format:

┌─────────────────────────────────────────────────────────────┐
│  SCP/1.0 | MSG_TYPE | id=MESSAGE_ID | PAYLOAD_DATA         │
└─────────────────────────────────────────────────────────────┘

Components:
  • SCP/1.0      → Protocol version identifier
  • MSG_TYPE     → Message type (HELLO, MSG, ACK, BYE, ERROR)
  • id=XXX       → Unique message identifier (integer)
  • PAYLOAD_DATA → Actual message content or status

Message Types

Type Direction Purpose Example
HELLO Client ↔ Server Initiate connection SCP/1.0 | HELLO | id=0 | ClientName
MSG Client ↔ Server Send chat message (bidirectional) SCP/1.0 | MSG | id=1 | Hello World
ACK Client ↔ Server Acknowledge receipt SCP/1.0 | ACK | id=1 | MSG_RECEIVED
BYE Client ↔ Server Terminate connection SCP/1.0 | BYE | id=99 | DISCONNECT
ERROR Client ↔ Server Report errors SCP/1.0 | ERROR | id=1 | INVALID_FORMAT

Duplex Communication Flow

CLIENT                                    SERVER
  │                                         │
  │──── HELLO (id=0) ──────────────────────>│  Connection Setup
  │<──── ACK (id=0) ────────────────────────│
  │                                         │
  │──── MSG (id=1, "Hi Server") ───────────>│  Client → Server
  │<──── ACK (id=1) ────────────────────────│
  │                                         │
  │<──── MSG (id=2, "Hi Client") ───────────│  Server → Client
  │──── ACK (id=2) ─────────────────────────>│
  │                                         │
  │──── MSG (id=3, "How are you?") ────────>│  Client → Server
  │  X   (packet lost)                      │  Timeout!
  │                                         │
  │──── MSG (id=3, "How are you?") ────────>│  Retry
  │<──── ACK (id=3) ────────────────────────│
  │                                         │
  │<──── MSG (id=4, "I'm good!") ───────────│  Server → Client
  │──── ACK (id=4) ─────────────────────────>│
  │                                         │
  │──── BYE (id=5) ─────────────────────────>│  Termination
  │<──── ACK (id=5) ────────────────────────│
  │                                         │
  │           [Connection Closed]           │

Reliability Mechanism

Acknowledgment System (Bidirectional)

  1. Sender (Client or Server) sends message with unique ID
  2. Sender starts timeout timer (e.g., 5 seconds)
  3. Receiver receives message and sends ACK with same ID
  4. Sender receives ACK → Success, clear timer
  5. If timeout expires → Resend message (up to MAX_RETRIES)
// Pseudocode for Duplex Send Logic
send_message(text, is_client):
    msg_id = generate_unique_id()
    retries = 0
    
    while retries < MAX_RETRIES:
        send(format_message("MSG", msg_id, text))
        
        if wait_for_ack(msg_id, TIMEOUT):
            print("✓ Message delivered")
            return SUCCESS
        else:
            retries++
            print("⚠ Timeout, retrying...")
    
    print("✗ Failed after max retries")
    return FAILURE

// Both client and server run this logic independently

🔧 How We Built This Project

Step 1: Protocol Design

We started by defining the message format, choosing a simple text-based structure with delimiters for easy parsing. The format includes version, message type, ID, and payload fields.

Step 2: Socket Programming in C

Implemented TCP socket creation, binding, listening, and connection acceptance on the server side. On the client side, we implemented socket creation and connection initiation.

Step 3: Message Parsing

Created functions to format and parse SCP messages using string manipulation (strtok, sprintf, sscanf) in C.

Step 4: Reliability Mechanism

Implemented timeout using setsockopt() with SO_RCVTIMEO, added retry logic with counters, and created ACK tracking with message IDs.

Step 5: Duplex Communication

Used POSIX threads (pthread) to create separate threads for sending and receiving, allowing both parties to communicate simultaneously.

Step 6: Testing & Visualization

Built an interactive HTML/CSS/JavaScript simulator to visualize protocol behavior, test different network conditions, and demonstrate packet loss handling.

🔄 Execution Flow

1. Server starts and waits for connections
2. Client connects and sends HELLO message
3. Server acknowledges with ACK
4. Both parties can now send messages bidirectionally
5. Each message is acknowledged by the receiver
6. If ACK not received, sender retries (up to 3 times)
7. Client sends BYE to disconnect gracefully

📊 Interpreting the Results

Message Format

Each line shows: [Timestamp] SEND/RECV: SCP/1.0 | TYPE | id=X | Payload

  • Timestamp: When the event occurred
  • SEND/RECV: Direction of message
  • TYPE: HELLO, MSG, ACK, BYE, or ERROR
  • id: Unique message identifier
  • Payload: Actual message content

Success Indicators

  • ✓ checkmark: Operation successful
  • "ACK received for id=X": Message delivered successfully
  • Green timestamps: Normal operation

Error Indicators

  • ⚠ warning: Timeout occurred
  • ✗ cross mark: Operation failed
  • "Retrying...": Attempting to resend message
  • "FAILED after X retries": Message could not be delivered
